# Release 12.16.53: do not wait for the full save drain

The 12.16.52 submit path joined cloudSaveTask. That promise drains every subsequently queued save, including study-time and screen-state updates. A submitted answer could already be committed while its grading remained blocked behind unrelated later writes. Actual new-version submissions still showed 9–11 seconds before grade start; one transient/retry case took 37 seconds before start. These intervals include transport/auth/dispatch, so they are not all attributable to the save loop.

The production save loop now notifies answer-specific waiters after each committed snapshot. A waiter requires the same account/auth epoch, lesson, original answer, payload and ready-question slot. It releases grading as soon as that answer is committed; later writes continue in the existing loop. Already committed answers need no additional save. Save failure/timeouts do not start AI, and polling/received results retain their previous paths. Authentication and answer-save confirmation run concurrently. No DB functions, permissions, grade hashes, AI models or learner results are changed.

The regression runs the actual production save-loop source with two writes: after the first commits, the grading waiter must resolve while the second write and full save promise remain unresolved. It also checks failed save, account switch, cached answer, status polling, and unchanged original answer. Full release and browser CI remain required. Actual AI/provider computation and the first necessary durable write can still take time.
